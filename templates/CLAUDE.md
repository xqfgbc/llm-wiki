# Wiki 维护契约

> 这份文件是给**读写的 LLM** 看的规则书，不是给人看的介绍。
> 编译 wiki 页、手工补页、以及回答问题时引用本 wiki，都必须遵守。
> 自动生成的文件（`index.md`、`log.md`）不要手工编辑。

---

## 一、这是什么

`wiki/` 是一层**派生物**，不是事实来源。事实来源永远是 `agent-security/` 之类被登记的 Obsidian 目录。
本目录下的每一句事实性断言，都必须能追回到某个源文档的某个小节。

## 二、目录

```
wiki/
├── CLAUDE.md          本文件（契约）
├── GLOSSARY.md        中英唯一译法 + 查询扩展来源
├── EXCLUSIONS.yaml    排除名单（人维护）
├── index.md           全站目录（自动生成）
├── log.md             操作日志（自动追加）
└── <collection>/
    ├── concepts/      概念页
    ├── entities/      实体页（产品、标准、组织）
    ├── topics/        主题综述页
    └── notes/         人工页，编译永不覆盖
```

## 三、页面结构（固定 7 段，顺序不得变更）

```markdown
# <标题>

> **一句话**：……【[[文档标题#小节标题]]】

## 定义与边界
## 关键构成
## 在本知识库中的证据
## 与其他页的关系
## 争议与不同说法
## 适用范围与局限
## 来源索引
```

- H1 唯一，且必须与 frontmatter 的 `title` 完全一致
- 除「来源索引」与「与其他页的关系」外，每个 H2 下至少一条引用
  （关系段是导航，靠双链承载，不要求引用；其余各节缺引用一律判为错误）
- 正文规模 ≤ 3000 字（引用标记不计）；超过就拆页或改用链接下钻

## 三之二、页面类型：什么时候用哪个

`type` 不是标签，它决定导航分组与检索标签。判定用一句话：

> **概念说「这个机制是什么」，实体说「这个具体东西是什么」，主题说「这些东西怎么拼起来用」。**

| 类型 | 回答什么 | 判定标准 | 例子 |
|---|---|---|---|
| `concept` | 是什么、为什么、边界在哪 | 抽象的机制、原则或问题，能脱离具体产品存在 | 凭证代理模式、最小权限、HITL |
| `entity` | 是谁、是哪个具体东西 | 可指称的具体对象：协议、产品、草案、清单 | MCP、AWS KMS、CB4A 草案 |
| `topic` | 怎么组合、怎么落地 | 需要重组多个已有概念或实体才讲得清的综述 | Agent 安全参考架构 |

操作判据（拿不准时按顺序问）：

1. 它能被一句「它是什么产品/哪份文档」指认吗？→ `entity`
2. 它讲的是一个机制，还是一个「该怎么建」的整体主张？→ 前者 `concept`，后者 `topic`
3. 它是否必须引用另外两个以上的已有页才能讲清？→ 是则 `topic`，否则 `concept`

**三类页共享同一套 7 段结构与引用契约**，type 只影响分组，不影响写作规则。

### 关系方向

- 概念之间是网状：横向互链是主结构
- 实体指向概念：用「我属于哪个机制」解释自己，而非「我和别的产品像不像」
- 主题聚合概念与实体：**概念页也要向上链到相关主题**，否则读者只能下钻、无法上卷

## 四、引用格式（唯一合法写法）

```
【[[文档标题#规范化小节标题]]】
```

- `文档标题` 可以是源文档 frontmatter 的 `title`，也可以是它的文件名（不含 `.md`）
- `小节标题` 必须是**规范化后的标题**——即 `data/raw/<collection>/*.map.json` 里 `norm` 字段的值，
  也是你在快照里实际读到的那一行
- 一条断言一个引用；同一段落的连续论据可以共用一个引用，但不允许整页只挂一个引用

**不合法**：`【[[]]】`、`【[[文档]]】`（缺小节）、`[链接](http://…)` 形式的引用、脚注编号。

## 五、语言

- 正文、标题、摘要**一律中文**
- 英文原文必须翻译后转述，不得整段照抄
- 专有名词保留英文：AWS KMS、OpenBao、agentgateway、MCP、OWASP、CB4A、RFC 8693
- 术语必须用 `GLOSSARY.md` 的「中文」列；禁用列里的写法一次都不许出现
- 正文 CJK 占比不得低于 0.45

## 六、什么不许写

1. 源文档里没有的事实、数字、时间
2. 把统计共现写成因果关系（「A 导致 B」，除非原文明确这么说）
3. 无出处的形容词：「显著提升」「行业领先」「大幅优化」
4. 对不同文档的分歧擅自裁决——分歧必须并列呈现

## 七、冲突处理

不同文档说法不一致时：

1. 在 `## 争议与不同说法` 里并列两方观点，各自带引用
2. 在 frontmatter 把 `status` 置为 `disputed`
3. 在 `stale_reason` 或正文里注明分歧点，不要二选一

被新文档取代的旧说法不要静默删除，标注「已被 X 取代」并保留引用。

## 八、frontmatter

```yaml
title: 凭证代理模式          # 必填，与 H1 一致
slug: credential-brokering   # 必填，小写连字符，全站唯一
type: concept                # concept | entity | topic | note
collection: agent-security   # 必填
aliases: [Credential Brokering, CB4A]
status: active               # active | stale | disputed | draft
compiled_by: llm-wiki/1
compiled_at: 2026-11-05T23:40:00
language: zh
sources:
  - doc: "源文档标题"
    cites:
      - heading: "规范化小节标题"
stale_reason: ""
```

`sources[].cites[]` 必须与正文引用**双向一致**：正文引用了却没声明、声明了却没引用，都会校验失败（后者只是警告）。

## 九、笔记与写回

有价值的对话、分析结论、人工判断需要沉淀时，写回 `notes/`。

### 先判断写回成什么

| 内容性质 | 写成 | 理由 |
|---|---|---|
| 结论能逐条追到原文 | `topic` 页，正常七段结构 + 引用 | 它能自证，属于知识 |
| 结论来自推理/讨论，原文没有直接对应 | `note` 页 | 强行引用会造成虚假依据 |
| 只是对某页的补充说明 | 直接改那一页，再 `stamp` | 不制造第二处事实 |

**不要为了「看起来有据」而给笔记硬挂引用**——那比不引用更糟。

### 笔记的契约

```yaml
type: note
origin: conversation | human | imported   # 必填，说明这份判断从哪来
sources: []                                # 允许为空；非空则正文必须真的引用
status: draft                              # 默认草稿，评审后再置 active
```

- **不要求七段结构**，但至少一个二级标题
- **不要求逐节引用**；若声明了 `sources`，正文必须引用到，否则判错
- 编译流程只读不写，`update` 永不覆盖笔记
- `index.md` 与站点单独归入「笔记」组

### 建笔记

```bash
"$WIKI_PYTHON" -m wikilib.cli note --title "为什么把凭证代理做成独立层" \
  --slug why-broker-as-layer --link "凭证代理模式,令牌库"
```

### 从笔记升级为正式页

当笔记里的判断后来被原文证实：

1. 复制到 `topics/` 或 `concepts/`，`type` 改为对应类型，去掉 `origin`
2. 按七段结构重写，逐条补引用
3. 删除原笔记（或保留为历史，`status: stale`）

**不要**直接把笔记的 `type` 改掉就算升级——结构校验会立刻失败，这是设计如此。

## 十、自检

写完一页后，跑：

```bash
"$WIKI_PYTHON" -m wikilib.cli lint --collection <collection> --strict
```

硬失败的规则（引用解析不到、结构不符、中文占比不足、命中禁用译法、超长、引用未声明、命名冲突）必须修完才算完成；警告项（孤儿页、红链、未使用来源）可以留待后续。
